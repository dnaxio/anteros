Replication copies documents from a tenant's **main database** to one or more **destination databases**. It is **one-way** (source → destination), **incremental** (only changed documents are transferred), and driven by a **date key** (default `updatedAt`).

```
Main database ──push──▶ Destination 1
Main database ──push──▶ Destination 2
_replication_  =  cursors + stats + tombstones
```

## Not a replacement for MongoDB replication

This engine is a **data copy**, not a cluster. It does not replace MongoDB's own replication (replica sets) and knows nothing about MongoDB's High Availability.

|                                      | This engine                                                  | MongoDB replica set                                |
| ------------------------------------ | ------------------------------------------------------------ | -------------------------------------------------- |
| Direction                            | **one-way** (source → destination)                           | bidirectional (primary ↔ secondaries)              |
| Automatic failover                   | ❌                                                           | ✅                                                 |
| Automatic promotion of a destination | ❌                                                           | ✅ (election)                                      |
| Read scaling from the copy           | ❌ (not designed for it — the copy is eventually consistent) | ✅ (secondaries)                                   |
| Consistency                          | **eventual** — driven by the schedule                        | atomic, ordered by the oplog                       |
| Purpose                              | off-site copy, disaster recovery, feeding another app        | availability, durability, zero-downtime operations |

**What it gives you**: a recent, independent copy of the data on another database. If the main database is lost, that copy is what you **restore from** — promote it manually (or point a new deployment at it) and repoint the tenant's URI.

**What it does not give you**: no automatic switchover. If the main database goes down, the engine does not detect it, does not promote a destination and does not redirect traffic — the application keeps talking to the URI it was given.

::prose-callout{variant="warning"}

**Failover and High Availability are configured in the tenant's `database.uri`** — MongoDB's own mechanism, e.g. `mongodb://host1,host2,host3/app?replicaSet=rs0&readPreference=primaryPreferred`. The destinations declared in `replication.destinations` are **not** part of that URI: they are copies, not members of the set.

::

Recovery also implies two things the engine does not do for you:

- **Recency** — the copy lags behind by up to one schedule interval (plus the run in progress). Size your RPO against `schedule`, knowing a disaster loses at least the last interval.
- **Indexes & validators** — only the two indexes the engine needs are created on the destination (the date cursor `{ key, _id }` and `{ createdAt, updatedAt }`). The collection's own indexes, unique constraints and schema validators must be applied there separately before serving traffic from a restored copy.

## Configuration

Replication is configured **per tenant** — each tenant has its own destinations and schedule.

```typescript
import { app } from "@anteros/core";

app.boot({
  server: {
    port: 4000,
  },
  tenants: [
    {
      id: "v1",
      dir: "v1",
      database: { uri: "mongodb://localhost:27017/main" },
      replication: {
        enabled: true,
        schedule: { cron: "*/5 * * * *" }, // or { interval: '5m' }
        key: "updatedAt", // incremental date key (default)
        batchSize: 1000, // documents per batch
        runOnBoot: true, // run once right after boot
        destinations: [
          {
            id: "backup", // unique id, used as the state key
            uri: "mongodb://host:27017/backup",
            name: "backup", // optional (defaults to the URI name)
            options: { maxPoolSize: 5 }, // optional MongoClient options
            collections: ["orders"], // optional: only these collections
            enabled: true,
          },
        ],
      },
    },
  ],
});
```

### Configuration options

| Option         | Type                                         | Default              | Description                                                                           |
| -------------- | -------------------------------------------- | -------------------- | ------------------------------------------------------------------------------------- |
| `enabled`      | `boolean`                                    | `true`               | Enable replication for this scope                                                     |
| `schedule`     | `{ cron }` \| `{ interval }`                 | `{ interval: '5m' }` | When to replicate. `cron` takes precedence over `interval`                            |
| `key`          | `string`                                     | `'updatedAt'`        | Date key used for incremental synchronization                                         |
| `batchSize`    | `number`                                     | `1000`               | Documents transferred per batch                                                       |
| `runOnBoot`    | `boolean`                                    | `true`               | Run a first replication right after boot (non-blocking)                               |
| `initialSync`  | `'full'` \| `'skip'` \| `'latest'` \| `Date` | `'full'`             | How the initial sync starts (see [Initial synchronization](#initial-synchronization)) |
| `destinations` | `Destination[]`                              | —                    | Destination databases (required)                                                      |

### Destination options

| Option        | Type                 | Default     | Description                                                          |
| ------------- | -------------------- | ----------- | -------------------------------------------------------------------- |
| `id`          | `string`             | —           | Unique identifier — used as the `_replication_` state key (required) |
| `uri`         | `string`             | —           | MongoDB connection string (required)                                 |
| `name`        | `string`             | URI name    | Database name override                                               |
| `options`     | `MongoClientOptions` | —           | Extra MongoDB client options (pool size, timeouts…)                  |
| `collections` | `string[]`           | all enabled | Restrict replication to these collection slugs                       |
| `enabled`     | `boolean`            | `true`      | Turn this destination off without removing it                        |

## Enabling a collection

A tenant's **own** collections are **opt-in**: only collections with `replication.enabled` are copied. The framework's collections are the opposite — replicated by default, excluded explicitly (see [Which collections are replicated](#which-collections-are-replicated)).

```typescript
import { define } from "@anteros/core";

export default define.Collection({
  slug: "orders",
  fields: [
    { name: "status", type: "enum", enumOptions: { items: ["draft", "paid"] } },
    { name: "total", type: "number", required: true },
  ],
  replication: {
    enabled: true,
    key: "updatedAt", // optional: override the date key
  },
});
```

| Option        | Type                                         | Default                   | Description                                     |
| ------------- | -------------------------------------------- | ------------------------- | ----------------------------------------------- |
| `enabled`     | `boolean`                                    | `false`                   | Opt this collection into replication (required) |
| `key`         | `string`                                     | `replication.key`         | Date key override for this collection           |
| `initialSync` | `'full'` \| `'skip'` \| `'latest'` \| `Date` | `replication.initialSync` | Initial sync override for this collection       |

**File collections** opt in the same way — `define.FileCollection({ replication: { enabled: true } })` — which replicates their **documents** (the metadata). Combine it with `replicate` to also copy the binaries. See [Files → Replication](/docs/reference/files#replication).

### Which collections are replicated

| Source                                                          | Replicated                                                    |
| --------------------------------------------------------------- | ------------------------------------------------------------- |
| Document collections (`{tenant.dir}/collections/**/*.model.ts`) | **opt-in** — `replication: { enabled: true }`                 |
| File collections (`files/**/*.file.ts`)                         | **opt-in** — `replication: { enabled: true }` (metadata only) |
| `_audit_`                                                       | **yes**, unless excluded — read on `ts`                       |
| `_workflows_`                                                   | **yes**, unless excluded — read on `updatedAt`                |
| `_locks_`                                                       | **yes**, unless excluded — read on `expiresAt`                |
| `_replication_`                                                 | **yes**, unless excluded — read on `updatedAt`                |
| `_vars_`                                                        | **yes**, unless excluded — **every** namespace, see below     |
| The agent memory collections                                    | **yes**, unless excluded — **the name you choose**, see below |

### Excluding framework collections

You opt out through a **typed list**:

```typescript
replication: {
  destinations: [{ id: "backup", uri: "mongodb://backup:27017/app" }],
  // 'audit' | 'workflows' | 'locks' | 'replication' | 'vars' | 'memory'
  exclude: ["locks", "replication"],
}
```

| Name          | Collection                   | Date key    | Typically excluded because…                                       |
| ------------- | ---------------------------- | ----------- | ----------------------------------------------------------------- |
| `audit`       | `_audit_`                    | `ts`        | most write-heavy collection — the copy doubles that traffic       |
| `workflows`   | `_workflows_`                | `updatedAt` | run state is high-churn (rewritten at every step)                 |
| `locks`       | `_locks_`                    | `expiresAt` | locks are ephemeral and node-specific — pure churn                |
| `replication` | `_replication_`              | `updatedAt` | you rarely want the cursors duplicated — see the caveat below     |
| `vars`        | `_vars_`                     | `updatedAt` | it carries **every** namespace, including the secret-bearing ones |
| `memory`      | the agent memory collections | `updatedAt` | agent conversations are **user data** — see below                 |

Each name is read with the key the framework itself uses (`_audit_` on `ts`, the rest on `updatedAt`), so a tenant-level `key` never breaks them. `exclude: ['audit']` removes that collection only — everything else keeps replicating. A destination can further restrict the set with its own `collections: ['orders', '_audit_']`.

::prose-callout{variant="warning"}

**`vars` now covers every namespace.** Replicating `_vars_` used to require a per-namespace `define.Vars({ replication: { enabled: true } })`; the tenant-level behaviour wins today, and a namespace is copied unless it declares `replication: { enabled: false }` — or unless you put `'vars'` in `exclude`. If any namespace holds secrets, licences or tokens, exclude `vars` (or opt that namespace out) explicitly.

::

::prose-callout{variant="warning"}

**`memory` names collections you chose.** An [agent memory](/docs/ai/memory) collection is the one you passed to `agents.memory.Mongo({ collection: … })`. The agent loader publishes it, and the engine copies it like a declared collection; `exclude: ['memory']` leaves **all** of them on the source. A store created outside the loader (a script, a test) is not published — declare a collection if you want it copied.

::

::prose-callout{variant="info"}

What the framework collections do — and do not — copy faithfully:

- **Deletions.** `_vars_` (an opted-in namespace) and an **agent memory collection** (a cleared thread, see [Memory](/docs/ai/memory)) **write a tombstone**, so their deletions propagate. `_audit_`, `_workflows_` and `_locks_` have no hooks and no tombstone: an entry removed on the source would stay on the destination forever — which is why the engine **mirrors the source retention on the destination** when `audit.retention` / `workflows.retention` is set.
- **Retention is not always mirrored.** The audit and workflow retentions are configuration, so the destination gets the same TTL index. An `agents.memory.Mongo({ ttl: '180d' })` is a **store** option: the source prunes itself and the destination keeps the threads. Prune the destination yourself (or do not set a TTL) if that matters.
- **`replication` is self-referential.** `_replication_` holds the state a node writes _for its own destinations_. Copying the source's state into a destination that is also a source can collide when both use the same destination id. Leave it out unless you are preparing a stand-by that will take over the cursors.

::

## How it works

### What is replicated

| Change   | Detection mechanism                                           |
| -------- | ------------------------------------------------------------- |
| `insert` | date cursor — new documents are picked up automatically       |
| `update` | date cursor — `updatedAt` is refreshed on every update        |
| `delete` | tombstone + hook — the only change invisible to a date cursor |

All three are **always replicated** — there is nothing to configure. `insert` and `update` need nothing special: both refresh the date key, so the incremental cursor picks them up (they are indistinguishable, and there is no reason to tell them apart). `delete` is different — a deleted document no longer exists, so a cursor comparing dates can never see it. Deletions are therefore captured in the background with a **hook + tombstone** (see below).

### Identity & types — copied verbatim

The destination document keeps the **exact same `_id`**, BSON type included: the write is an upsert keyed on it (`replaceOne({ filter: { _id }, replacement: doc, upsert: true })`), and deletes target it too (`{ _id }`).

```
source: { _id: ObjectId('68c…'), ref: 'A-1' }      →  destination: { _id: ObjectId('68c…'), ref: 'A-1' }
source: { _id: 'order-42', ref: 'A-2' }            →  destination: { _id: 'order-42', ref: 'A-2' }
```

Documents are read from the source through the **raw driver** and written back as they are — nothing is converted to JSON along the way. Every BSON type therefore survives the copy:

| Source                                           | Destination        |
| ------------------------------------------------ | ------------------ |
| `_id: ObjectId`                                  | `_id: ObjectId`    |
| relation field (`ObjectId`, or an array of them) | same `ObjectId`(s) |
| `date` field (`Date`)                            | `Date`             |
| `createdAt` / `updatedAt`                        | `Date`             |
| `_id: 'string'` (non-hex)                        | `_id: 'string'`    |

The document is **replaced as a whole** (not merged): the destination is a mirror of the source, so a field removed at the source disappears at the destination on the next run.

::prose-callout{variant="info"}

The copy is **faithful, not corrective**: whatever the source holds is what the destination gets. Types are normalised at _write_ time on the source by `toBson` (a relation id sent as a string becomes an `ObjectId`, an ISO date becomes a `Date`) — so a value that is a string in the source will be a string in the destination too. If you see strings where you expect `ObjectId`, the source write path is the place to look.

::

::prose-callout{variant="warning"}

Because the `_id` is reused as-is, two sources writing to the **same destination collection** overwrite each other's documents (last write wins). Keep one destination collection per tenant/collection pair.

::

### Incremental cursor

Replication keeps a **compound cursor `(key, _id)`** per `(tenant, destination, collection)`. The `_id` tie-breaker guarantees that documents sharing the same timestamp are neither skipped nor duplicated:

```typescript
const filter = {
  $or: [
    { [key]: { $gt: cursor.value } },
    { [key]: cursor.value, _id: { $gt: cursor.id } },
  ],
};
const sort = { [key]: 1, _id: 1 };
```

Each run reads documents newer than the cursor, writes them to the destination with an upsert on `_id` (`replaceOne`, `upsert: true`), then advances the cursor to the last transferred document. The cursor is persisted after every batch, so a crash resumes where it stopped.

::prose-callout{variant="info"}

**Indexes** — a `{ [key]: 1, _id: 1 }` index is created automatically on the source collection (so the incremental query never scans the whole collection) and on each destination collection.

::

### Insert & update

`insert` and `update` go through the **exact same path** — the incremental cursor. Both refresh `updatedAt`, so both appear as "documents newer than the cursor". The `_id`-based upsert decides what actually happens on the destination:

| Source change | `_id` on destination? | Result                                |
| ------------- | --------------------- | ------------------------------------- |
| `insert`      | no                    | `upsertedCount` +1 (new document)     |
| `update`      | yes                   | `matchedCount` +1 (document replaced) |

Step by step:

1. `find({ updatedAt > cursor.value }` or `{ updatedAt == cursor.value and _id > cursor.id })`, sorted by `(updatedAt, _id)`, limited to `batchSize`.
2. `bulkWrite` of `replaceOne({ _id }, doc, { upsert: true })` for each document.
3. Advance the cursor to the last transferred document and persist it in `_replication_`.
4. Repeat while a full batch was returned; otherwise mark the run `success`.

Example — cursor is `{ value: 10:00:00, id: _id=100 }`; between two runs `_id=101` is inserted (`updatedAt = 10:00:01`) and `_id=102` is updated (`updatedAt = 10:00:01`). The next run fetches both, **inserts** `_id=101` and **replaces** `_id=102`, then advances the cursor to `{ 10:00:01, _id=102 }`.

### Deletes (hook + tombstone)

Deletes are **always propagated**. On every sync-enabled collection, the `afterOperation` hook is wrapped in the background (chaining the user hook, never replacing it). On `deleteOne`/`deleteMany`, a **tombstone** is written to `_replication_`. The next run reads pending tombstones, deletes the corresponding documents on the destination, and marks the tombstone as `synced`.

```
deleteOne  →  afterOperation hook  →  tombstone in _replication_  →  next run  →  deleteMany on destination  →  mark synced
```

### Initial synchronization

By default, the first run **backfills everything** (the cursor starts empty). Use `initialSync` to control how replication starts — notably to skip the full backfill when the destination is already pre-loaded (e.g. after a `mongodump`/`mongorestore`).

| Value                | Behavior                                                                   |
| -------------------- | -------------------------------------------------------------------------- |
| `'full'` _(default)_ | Backfill everything — every existing document is copied                    |
| `'skip'`             | Skip the initial sync — start from now, only future changes                |
| `'latest'`           | Start from the latest `updatedAt` in the source — skip everything existing |
| ISO string / `Date`  | Start from that date — only documents newer than it are copied             |

```typescript
replication: {
  initialSync: "latest",   // or 'full', 'skip', or '2026-01-01T00:00:00Z'
  destinations: [{ id: "backup", uri: "mongodb://host:27017/backup" }],
}
```

`initialSync` is resolved **only when no `_replication_` state exists** (first run). Once the cursor is persisted, it is ignored.

## The `_replication_` collection

Replication state is stored in the **`_replication_`** collection of each tenant's **main database**. Two kinds of documents coexist, discriminated by `type`.

### State document

One per `(tenant, destination, collection)` — `_id` is `rep:{tenant}:{destination}:{collection}`:

```json
{
  "_id": "rep:v1:backup:orders",
  "type": "state",
  "tenant": "v1",
  "destination": "backup",
  "collection": "orders",
  "key": "updatedAt",
  "cursor": { "value": "2026-09-19T10:00:00.000Z", "id": "..." },
  "status": "success",
  "lastRunAt": "2026-09-19T10:05:00.000Z",
  "lastError": null,
  "stats": {
    "inserted": 0,
    "updated": 0,
    "deleted": 0,
    "batches": 0,
    "durationMs": 12
  },
  "updatedAt": "2026-09-19T10:05:00.000Z"
}
```

### Delete tombstone

One per deleted document — `_id` is `rep.delete:{tenant}:{collection}:{docId}`:

```json
{
  "_id": "rep.delete:v1:orders:6512...",
  "type": "delete",
  "tenant": "v1",
  "collection": "orders",
  "docId": "6512...",
  "deletedAt": "2026-09-19T10:04:00.000Z",
  "synced": ["backup"],
  "updatedAt": "2026-09-19T10:04:00.000Z"
}
```

## Scheduler

- `schedule.cron` → uses `Bun.cron` (a cron expression, e.g. `'*/5 * * * *'`).
- `schedule.interval` → a human interval (`'30s'`, `'5m'`, `'2h'`, `'1d'`) or milliseconds.

A reentrancy guard prevents two overlapping runs for the same `(tenant, destination)`.

## Boot modes

What a process runs is described by four **capabilities** — `api`, `replication`, `scripts`, `sockets` — driven by `server.mode` (config) and by flags (**the flags always win**):

|                      | Flag                            | `server.mode`        | api | replication | scripts | sockets |
| -------------------- | ------------------------------- | -------------------- | --- | ----------- | ------- | ------- |
| Everything (default) | —                               | `'full'`             | ✅  | ✅          | ✅      | ✅      |
| Replication only     | `--replication-only`            | `'replication-only'` | ❌  | ✅          | ❌      | ❌      |
| API only             | `--api-only`                    | `'api-only'`         | ✅  | ❌          | ❌      | ❌      |
| No replication       | `--no-replication`              | `'no-replication'`   | ✅  | ❌          | ✅      | ✅      |
| Granular             | `--no-scripts` · `--no-sockets` | —                    | ✅  | ✅          | ❌      | ✅      |

```bash
bun index.ts                        # full
bun index.ts --replication-only     # a process dedicated to replication
bun index.ts --api-only             # the API and nothing around it
bun index.ts --no-replication       # a server that never starts the engine
bun index.ts --no-scripts           # a server that never runs the tenant scripts
bun index.ts --no-sockets           # a server without Socket.IO
bun index.ts --no-scripts --no-sockets
```

```typescript
app.boot({ server: { mode: "api-only" }, tenants: [/* … */] });
```

`api: false` also disables what the HTTP server carries (services, MCP tools, middlewares, routes, sockets) and the scripts, which run alongside it. `--replication-only` wins over `--no-replication` / `--api-only` when combined, and a warning is printed.

The banner only shows a `Mode:` line when something is disabled:

```
Replication: Off (api-only)
Mode: api-only (replication, scripts, sockets off)
Url: http://localhost:4000
```

### Replication-only process

It **exposes no API at all** — no HTTP server, no websocket handlers, no scripts, no services, no MCP tools, no middlewares. Useful to keep replicating from a host that must not serve traffic, to isolate replication from the application, or to run it in its own systemd/PM2 unit.

|               | Runs                                                                                                                                | Skipped                                                                                     |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **Loaders**   | tenant databases, collections, file collections, variables (`_vars_` replication filters on them), lifecycle                        | services, sockets, workflows, MCP tools, middlewares, routes, `createApp()` / `Bun.serve()` |
| **Lifecycle** | `beforeBoot` (before replication starts — the place to seed/reset it), `onDestroy` (on `SIGINT`/`SIGTERM`, after replication stops) | `afterBoot` (there is no listening server)                                                  |
| **Runtime**   | replication schedule, tombstones, distributed lock                                                                                  | `runScripts()`, cluster (master/workers), metrics & `/health`, JWT secret bootstrap         |

The process keeps itself alive (replication timers are `unref`'d, so a keep-alive handle is held) and shuts down cleanly on `SIGINT`/`SIGTERM`: `onDestroy` hooks, then `stopReplication()`, then the database clients are closed.

### Who replicates

A run is guarded by a **distributed lock** (`_locks_`, one per `(tenant, destination)`), so only one process replicates a given destination at a time — even when several run the same code (Bun `reusePort`, forked workers, several containers).

The lock stores the **`pid`** and **`hostname`** of its owner, and so does every state document in `_replication_` (`pid`, `hostname`): you can see at a glance which process did what.

- a lock whose owner **died on the same host** is taken over **immediately** (the pid is probed) — a crashed worker never blocks replication for the whole TTL;
- a lock owned by **another host** can only be taken over once it expires (a foreign pid cannot be probed);
- releasing a lock only ever removes **our own** — a lock taken over by another node is never deleted from under it.

### No-replication / API-only processes

A **full** server — API, sockets, services, routes, scripts, MCP, middlewares, cluster, metrics — that simply **never starts the replication engine**: no scheduling, no `_replication_` collection, no tombstones, no distributed lock. Nothing is written to the destination databases.

Use it when the same codebase is deployed in places that must not replicate (a read replica of the app, a staging environment pointed at production data, a machine where the destinations are unreachable) without stripping the tenant configuration. Per-tenant opt-out (`replication.enabled`) remains the finer-grained tool; `--no-replication` is the blunt, process-wide one. `--api-only` adds to that: no scripts, and Socket.IO is not served at all (`/socket.io/` answers like any unknown path).

## API

The replication engine is exposed under the `replication` namespace (like `cache`):

```typescript
import { replication } from "@anteros/core";

replication.start(); // start scheduling (idempotent)
replication.stop(); // stop scheduling + close destination clients
await replication.now("v1"); // run manually (optionally a destination/collection)
const state = await replication.state("v1", "backup"); // read _replication_ state
await replication.reset("v1"); // forget progress — next run starts over
await replication.seed("v1", "latest"); // (re)start from a given point
```

| Method                                        | Description                                               |
| --------------------------------------------- | --------------------------------------------------------- |
| `replication.start()`                         | Connect destinations and start the scheduler (idempotent) |
| `replication.stop()`                          | Stop the scheduler and close destination clients          |
| `replication.now(tenantId?, opts?)`           | Trigger a run manually                                    |
| `replication.state(tenantId, destinationId?)` | Read replication state from `_replication_`               |
| `replication.reset(tenantId, opts?)`          | Forget a tenant's replication progress (see below)        |
| `replication.seed(tenantId, value, opts?)`    | Set the starting point of replication (see below)         |

### Resetting replication

`replication.reset()` deletes the `_replication_` **state** (cursor, stats, status), so the next run starts over. The destination data is **never** touched — only the bookkeeping is cleared.

```typescript
await replication.reset("v1"); // every destination + collection
await replication.reset("v1", { destination: "backup" }); // one destination
await replication.reset("v1", { collection: "orders" }); // one collection
await replication.reset("v1", { tombstones: false }); // keep pending deletes
```

| Option        | Type      | Default | Description                                                                                                           |
| ------------- | --------- | ------- | --------------------------------------------------------------------------------------------------------------------- |
| `destination` | `string`  | all     | Only reset this destination id                                                                                        |
| `collection`  | `string`  | all     | Only reset this collection slug                                                                                       |
| `tombstones`  | `boolean` | `true`  | Also delete pending delete tombstones — ignored when `destination` is set (tombstones are shared across destinations) |

**Returns** `{ tenant, state, tombstones }` — the number of documents deleted from each kind.

After a reset, the next run replays according to `initialSync` (`'full'` re-backfills everything, `'skip'`/`'latest'` resume without backfilling).

### Setting the start point

`replication.seed()` writes the `_replication_` cursor directly — the counterpart of `reset()`. Use it to (re)start a replication from a given point instead of backfilling. The date field is the collection's replication key (`replication.key`, default `updatedAt`).

```typescript
await replication.seed("v1", "latest"); // from the latest document — skip existing
await replication.seed("v1", "now"); // from now — only future changes
await replication.seed("v1", "2026-01-01T00:00:00Z"); // from a date
await replication.seed("v1", new Date("2026-01-01")); // from a Date

// Scope + optional _id tie-breaker
await replication.seed("v1", "latest", {
  destination: "backup",
  collection: "orders",
});
```

| Value               | Behavior                                       |
| ------------------- | ---------------------------------------------- |
| `"now"`             | Start from now (same as `initialSync: 'skip'`) |
| `"latest"`          | Start from the latest `key` in the source      |
| ISO string / `Date` | Start from this date                           |

| Option        | Type     | Default | Description                |
| ------------- | -------- | ------- | -------------------------- |
| `destination` | `string` | all     | Only seed this destination |
| `collection`  | `string` | all     | Only seed this collection  |
| `id`          | `any`    | —       | Optional `_id` tie-breaker |

**Returns** `{ tenant, seeded }` — the number of state documents written.

::prose-callout{variant="info"}

`reset()` + `seed()` are typically called from a **lifecycle `beforeBoot` hook** — where `replication` is tenant-scoped (like `rest`, no tenant id) — so a tenant can decide its starting point before replication starts. See [Lifecycle](/docs/reference/lifecycle).

::

## Limitations & notes

- **`_id` type consistency** — the cursor tie-breaker compares `_id` values, so a collection should use a single `_id` type (e.g. `ObjectId`). Mixing types produces undefined ordering. Inserts and updates always carry the exact same `_id`; for **deletes**, the id round-trips through the tombstone as a string and is re-parsed as an `ObjectId` when valid — so a **string `_id` that looks like an `ObjectId`** (24 hex characters) would be searched as an `ObjectId` on the destination and the deletion would not match. Use `ObjectId` ids, or string ids that are not 24-hex.
- **Out-of-order writes / clock skew** — `updatedAt` should be set server-side; if multiple writers use different clocks, consider adding a small look-back window.
- **Initial backfill** — the first run copies the whole collection; it is batched and resumable, but large collections should be scheduled outside peak traffic.
- **Not a failover mechanism** — this engine copies data one way; availability, failover and promotion are MongoDB's job (replica set configured in the tenant's `database.uri`). See [Not a replacement for MongoDB replication](#not-a-replacement-for-mongodb-replication).
