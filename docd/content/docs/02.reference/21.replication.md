Replication copies documents from a tenant's **main database** to one or more **destination databases**. It is **one-way** (source → destination), **incremental** (only changes are transferred), and driven by **MongoDB change streams**: the engine tails the oplog of every replicated collection and applies each event as it is committed.

```
Main database ──push──▶ Destination 1
Main database ──push──▶ Destination 2
_replication_  =  resume tokens + backfill position + stats
```

## Not a replacement for MongoDB replication

This engine is a **data copy**, not a cluster. It does not replace MongoDB's own replication (replica sets) and knows nothing about MongoDB's High Availability.

|                                      | This engine                                                  | MongoDB replica set                                |
| ------------------------------------ | ------------------------------------------------------------ | -------------------------------------------------- |
| Direction                            | **one-way** (source → destination)                           | bidirectional (primary ↔ secondaries)              |
| Automatic failover                   | ❌                                                           | ✅                                                 |
| Automatic promotion of a destination | ❌                                                           | ✅ (election)                                      |
| Read scaling from the copy           | ❌ (not designed for it — the copy is eventually consistent) | ✅ (secondaries)                                   |
| Consistency                          | **eventual** — ordered by the oplog, applied as it arrives   | atomic, ordered by the oplog                       |
| Purpose                              | off-site copy, disaster recovery, feeding another app        | availability, durability, zero-downtime operations |

**What it gives you**: a recent, independent copy of the data on another database. If the main database is lost, that copy is what you **restore from** — promote it manually (or point a new deployment at it) and repoint the tenant's URI.

**What it does not give you**: no automatic switchover. If the main database goes down, the engine does not detect it, does not promote a destination and does not redirect traffic — the application keeps talking to the URI it was given.

::prose-callout{variant="warning"}

**Failover and High Availability are configured in the tenant's `database.uri`** — MongoDB's own mechanism, e.g. `mongodb://host1,host2,host3/app?replicaSet=rs0&readPreference=primaryPreferred`. The destinations declared in `replication.destinations` are **not** part of that URI: they are copies, not members of the set.

::

Recovery also implies two things the engine does not do for you:

- **Recency** — a copy lags by the time it takes to apply an event (milliseconds to a second), and it replays from its last position after a restart. Size your RPO against the **oplog window** — see [Limitations & notes](#limitations-notes).
- **Indexes & validators** — only the two indexes the engine needs are created on the destination (`{ [key]: 1, _id: 1 }` and `{ createdAt: -1, updatedAt: -1 }`). The collection's own indexes, unique constraints and schema validators must be applied there separately before serving traffic from a restored copy.

## Requirements

**The source must be a replica set or a sharded cluster.** Change streams read the oplog, and a standalone `mongod` does not have one.

::prose-callout{variant="warning"}

There is **no fallback**. When the source cannot serve change streams, the engine logs

```
replication: change streams unavailable — a replica set is required, tenant skipped
```

and **does not replicate that tenant**: nothing is written to its destinations. A date-key scan was the historical fallback, and it was removed because it cannot see a deletion — it would let the destination diverge silently instead of failing loudly.

::

```bash
# A one-node replica set is enough for a single server.
mongod --replSet rs0
mongosh --eval 'rs.initiate()'
```

## Configuration

Replication is configured **per tenant** — each tenant has its own destinations.

```typescript
import { app } from "@anteros/core";

app.boot({
  server: {
    port: 4000,
  },
  tenants: [
    {
      id: "v1",
      dir: "v1",
      database: { uri: "mongodb://localhost:27017/main" },
      replication: {
        enabled: true,
        key: "updatedAt", // the key the initial backfill reads the source in
        batchSize: 1000, // documents per backfill batch
        runOnBoot: true, // backfill what nobody has seeded right after boot
        destinations: [
          {
            id: "backup", // unique id, used as the state key
            uri: "mongodb://host:27017/backup",
            name: "backup", // optional (defaults to the URI name)
            options: { maxPoolSize: 5 }, // optional MongoClient options
            collections: ["orders"], // optional: only these collections
            enabled: true,
          },
        ],
      },
    },
  ],
});
```

### Configuration options

| Option         | Type                                         | Default      | Description                                                          |
| -------------- | -------------------------------------------- | ------------ | -------------------------------------------------------------------- |
| `enabled`      | `boolean`                                    | `true`       | Enable replication for this scope                                    |
| `key`          | `string`                                     | `'updatedAt'` | Date field the **initial backfill** reads the source in             |
| `batchSize`    | `number`                                     | `1000`       | Documents transferred per backfill batch                             |
| `runOnBoot`    | `boolean`                                    | `true`       | Backfill what was never seeded right after boot (non-blocking)       |
| `initialSync`  | `'full'` \| `'skip'` \| `'latest'` \| `Date` | `'full'`     | How the initial sync starts (see [Initial synchronization](#initial-synchronization)) |
| `destinations` | `Destination[]`                              | —            | Destination databases (required)                                     |

## How changes are detected

One stream per **replicated collection** stays open for the lifetime of the process. Each event is applied on the destination as it arrives:

|                          | Change streams                                     |
| ------------------------ | -------------------------------------------------- |
| How changes are detected | MongoDB **change streams** (the oplog)              |
| Latency                  | real-time (as the write is committed)               |
| Position kept            | a **resume token** per collection                   |
| Deleted documents        | seen in the oplog — **including a TTL expiry**      |
| `key`                    | initial backfill only (default `updatedAt`)         |
| `batchSize`              | initial backfill only                               |
| Requires                 | a **replica set** or a sharded cluster              |

### What a stream does in practice

- **Nothing has to be triggered.** There is no scheduler: the streams are the engine. A write on the source reaches the destination on its own.
- **Deletes come from the oplog.** A `delete` event carries the `_id` typed as it was written, so it is deleted as-is on the destination — no string round-trip, no tombstone. This covers the collections **without hooks**: an `_audit_` or `_workflows_` entry removed by its TTL index disappears from the destination too, and so does a variable, a cleared agent thread or a deleted file-collection document (their delete paths bypass the collection hooks, but the oplog sees them anyway).
- **One writer per collection.** The stream holds a `_locks_` lock per `(destination, collection)` for as long as it watches, and heartbeats it — so `runOnBoot` / `replication.now()` never backfill a collection the stream owns, and two cluster nodes never replay the same oplog onto the same destination. A run that finds the lock taken **skips that collection** and says so in the log. Run `replication.reset()` to re-arm a stream and backfill again.
- **The first run still backfills.** A stream only carries changes from the moment it starts, so a collection with no position yet (first boot, after `reset()`, after `seed()`) is **backfilled first**, then tailed. The stream's starting point is taken _before_ the backfill, so a write that lands during it is replayed instead of being lost — the upsert is idempotent, a lost event is not.
- **Recovery uses the resume token.** After a restart, control plane failover or a transient driver error, the stream reopens from the last persisted token (at most 5 seconds of events are replayed, all idempotent). If the token has fallen out of the **oplog window** (or the replica set was rolled back), the stream restarts from now and logs it: what happened in between is not replayed — run `replication.reset()` for a full rescan.
- **`seed()` sets where the backfill starts.** A seeded position (a date, `'latest'`, `'now'`) becomes the stream's new cold-start point: it stops, backfills from what you seeded, then keeps tailing from there.

::prose-callout{variant="warning"}

A change stream writes a **resume token** into `_replication_` (at most once every 5 seconds per collection) and `_replication_` is replicated by default. If you would rather not copy that bookkeeping, add `'replication'` to `exclude`.

::

### Destination options

| Option        | Type                 | Default     | Description                                                          |
| ------------- | -------------------- | ----------- | -------------------------------------------------------------------- |
| `id`          | `string`             | —           | Unique identifier — used as the `_replication_` state key (required) |
| `uri`         | `string`             | —           | MongoDB connection string (required)                                 |
| `name`        | `string`             | URI name    | Database name override                                               |
| `options`     | `MongoClientOptions` | —           | Extra MongoDB client options (pool size, timeouts…)                  |
| `collections` | `string[]`           | all enabled | Restrict replication to these collection slugs                       |
| `enabled`     | `boolean`            | `true`      | Turn this destination off without removing it                        |

## Enabling a collection

A tenant's **own** collections are **opt-in**: only collections with `replication.enabled` are copied. The framework's collections are the opposite — replicated by default, excluded explicitly (see [Which collections are replicated](#which-collections-are-replicated)).

```typescript
import { define } from "@anteros/core";

export default define.Collection({
  slug: "orders",
  fields: [
    { name: "status", type: "enum", enumOptions: { items: ["draft", "paid"] } },
    { name: "total", type: "number", required: true },
  ],
  replication: {
    enabled: true,
    key: "updatedAt", // optional: override the backfill key
  },
});
```

| Option        | Type                                         | Default                   | Description                                    |
| ------------- | -------------------------------------------- | ------------------------- | ---------------------------------------------- |
| `enabled`     | `boolean`                                    | `false`                   | Opt this collection into replication (required) |
| `key`         | `string`                                     | `replication.key`         | Backfill key override for this collection      |
| `initialSync` | `'full'` \| `'skip'` \| `'latest'` \| `Date` | `replication.initialSync` | Initial sync override for this collection      |

**File collections** opt in the same way — `define.FileCollection({ replication: { enabled: true } })` — which replicates their **documents** (the metadata). Combine it with `replicate` to also copy the binaries. See [Files → Replication](/docs/reference/files#replication).

### Which collections are replicated

| Source                                                          | Replicated                                                    |
| --------------------------------------------------------------- | ------------------------------------------------------------- |
| Document collections (`{tenant.dir}/collections/**/*.model.ts`) | **opt-in** — `replication: { enabled: true }`                 |
| File collections (`files/**/*.file.ts`)                         | **opt-in** — `replication: { enabled: true }` (metadata only) |
| `_audit_`                                                       | **yes**, unless excluded — backfilled on `ts`                 |
| `_workflows_`                                                   | **yes**, unless excluded — backfilled on `updatedAt`          |
| `_locks_`                                                       | **yes**, unless excluded — backfilled on `expiresAt`          |
| `_replication_`                                                 | **yes**, unless excluded — backfilled on `updatedAt`          |
| `_vars_`                                                        | **yes**, unless excluded — **every** namespace, see below     |
| The agent memory collections                                    | **yes**, unless excluded — **the name you choose**, see below |

### Excluding framework collections

You opt out through a **typed list**:

```typescript
replication: {
  destinations: [{ id: "backup", uri: "mongodb://backup:27017/app" }],
  // 'audit' | 'workflows' | 'locks' | 'replication' | 'vars' | 'memory'
  exclude: ["locks", "replication"],
}
```

| Name          | Collection                   | Backfill key | Typically excluded because…                                       |
| ------------- | ---------------------------- | ------------ | ----------------------------------------------------------------- |
| `audit`       | `_audit_`                    | `ts`         | most write-heavy collection — the copy doubles that traffic       |
| `workflows`   | `_workflows_`                | `updatedAt`  | run state is high-churn (rewritten at every step)                 |
| `locks`       | `_locks_`                    | `expiresAt`  | locks are ephemeral and node-specific — pure churn                |
| `replication` | `_replication_`              | `updatedAt`  | you rarely want the state duplicated — see the caveat below       |
| `vars`        | `_vars_`                     | `updatedAt`  | it carries **every** namespace, including the secret-bearing ones |
| `memory`      | the agent memory collections | `updatedAt`  | agent conversations are **user data** — see below                 |

Each name is backfilled with the key the framework itself uses (`_audit_` on `ts`, the rest on `updatedAt`), so a tenant-level `key` never breaks them. `exclude: ['audit']` removes that collection only — everything else keeps replicating. A destination can further restrict the set with its own `collections: ['orders', '_audit_']`.

::prose-callout{variant="info"}

`exclude` is read **when a watcher starts**. Changing it at runtime takes effect on the next `replication.stop()` / `replication.start()` (or a reboot) — a running stream does not re-read the list.

::

::prose-callout{variant="warning"}

**`vars` now covers every namespace.** Replicating `_vars_` used to require a per-namespace `define.Vars({ replication: { enabled: true } })`; the tenant-level behaviour wins today, and a namespace is copied unless it declares `replication: { enabled: false }` — or unless you put `'vars'` in `exclude`. If any namespace holds secrets, licences or tokens, exclude `vars` (or opt that namespace out) explicitly.

::

::prose-callout{variant="warning"}

**`memory` names collections you chose.** An [agent memory](/docs/ai/memory) collection is the one you passed to `agents.memory.Mongo({ collection: … })`. The agent loader publishes it, and the engine copies it like a declared collection; `exclude: ['memory']` leaves **all** of them on the source. A store created outside the loader (a script, a test) is not published — declare a collection if you want it copied.

::

::prose-callout{variant="info"}

What the framework collections do — and do not — copy faithfully:

- **Deletions.** The oplog carries them: a deletion on any replicated collection — a TTL expiry included — is applied on the destination, so `_audit_`, `_workflows_` and `_locks_` stay in step with no extra machinery. The destination also gets the source's audit and workflow **retention index** (`audit.retention` / `workflows.retention`), so a restored or re-seeded destination prunes itself even before the deletes are replayed.
- **A store's own `ttl` is a store option.** An `agents.memory.Mongo({ ttl: '180d' })` prunes the source; the deletes are replicated as they happen, so the destination follows — but the destination has no TTL index of its own.
- **`replication` is self-referential.** `_replication_` holds the state a node writes _for its own destinations_. Copying the source's state into a destination that is also a source can collide when both use the same destination id. Leave it out unless you are preparing a stand-by that will take over the resume tokens.

::

## How it works

### What is replicated

All three changes are carried by the stream — there is nothing to configure:

| Change   | How it travels                                                  |
| -------- | --------------------------------------------------------------- |
| `insert` | oplog event, applied as it is committed                          |
| `update` | oplog event carrying the post-image (`updateLookup`)             |
| `delete` | oplog event — **any** deletion, a TTL expiry included            |

An insert and an update both end in the same write on the destination — `replaceOne({ _id }, doc, { upsert: true })` — so the `_id` decides what actually happens. A delete targets `{ _id }` directly, with the `_id` exactly as the oplog carries it.

### Identity & types — copied verbatim

The destination document keeps the **exact same `_id`**, BSON type included: the write is an upsert keyed on it, and deletes target it too.

```
source: { _id: ObjectId('68c…'), ref: 'A-1' }      →  destination: { _id: ObjectId('68c…'), ref: 'A-1' }
source: { _id: 'order-42', ref: 'A-2' }            →  destination: { _id: 'order-42', ref: 'A-2' }
```

Documents are carried by the oplog and written back as they are — nothing is converted to JSON along the way. Every BSON type therefore survives the copy:

| Source                                           | Destination        |
| ------------------------------------------------ | ------------------ |
| `_id: ObjectId`                                  | `_id: ObjectId`    |
| relation field (`ObjectId`, or an array of them) | same `ObjectId`(s) |
| `date` field (`Date`)                            | `Date`             |
| `createdAt` / `updatedAt`                        | `Date`             |
| `_id: 'string'` (non-hex)                        | `_id: 'string'`    |

The document is **replaced as a whole** (not merged): the destination is a mirror of the source, so a field removed at the source disappears at the destination on the next event that touches the document.

::prose-callout{variant="info"}

The copy is **faithful, not corrective**: whatever the source holds is what the destination gets. Types are normalised at _write_ time on the source by `toBson` (a relation id sent as a string becomes an `ObjectId`, an ISO date becomes a `Date`) — so a value that is a string in the source will be a string in the destination too. If you see strings where you expect `ObjectId`, the source write path is the place to look.

::

::prose-callout{variant="warning"}

Because the `_id` is reused as-is, two sources writing to the **same destination collection** overwrite each other's documents (last write wins). Keep one destination collection per tenant/collection pair.

::

### Backfill

A stream only sees what happens **after** it starts, so a collection that has never been seeded is copied first. The backfill is a resumable pass over the source, in batches of `batchSize`, ordered by `(key, _id)`:

```typescript
const filter = {
  $or: [
    { [key]: { $gt: cursor.value } },
    { [key]: cursor.value, _id: { $gt: cursor.id } },
  ],
};
const sort = { [key]: 1, _id: 1 };
```

The `(key, _id)` pair is the **backfill position** — the `cursor` field of the state document. It is persisted after every batch, so a crash resumes where it stopped. The `_id` tie-breaker guarantees that documents sharing the same timestamp are neither skipped nor duplicated.

The pass runs:

- when a stream cold-starts (no resume token: a fresh tenant, after `reset()`, after `seed()`), then the stream takes over from where the backfill began;
- from `replication.now()` / `runOnBoot`, but **only** for a collection nobody has seeded — a collection a stream already owns is skipped, so a stale read can never overwrite a newer event.

::prose-callout{variant="info"}

**Indexes** — a `{ [key]: 1, _id: 1 }` index is created automatically on the source collection (so the backfill query never scans the whole collection) and on each destination collection.

::

### Initial synchronization

By default, the backfill **copies everything**. Use `initialSync` to control how a cold start begins — notably to skip the full copy when the destination is already pre-loaded (e.g. after a `mongodump`/`mongorestore`).

| Value                | Behavior                                                                    |
| -------------------- | --------------------------------------------------------------------------- |
| `'full'` _(default)_ | Backfill everything — every existing document is copied                     |
| `'skip'`             | Skip the initial sync — start from now, only future changes                 |
| `'latest'`           | Start from the latest `key` in the source — skip everything existing        |
| ISO string / `Date`  | Start from that date — only documents newer than it are copied              |

```typescript
replication: {
  initialSync: "latest",   // or 'full', 'skip', or '2026-01-01T00:00:00Z'
  destinations: [{ id: "backup", uri: "mongodb://host:27017/backup" }],
}
```

`initialSync` is resolved **only when there is no position to resume from** — a cold start, or after `reset()` / `seed()`. Once a backfill position (or a resume token) is persisted, it is ignored.

## The `_replication_` collection

Replication state is stored in the **`_replication_`** collection of each tenant's **main database**, one document per `(tenant, destination, collection)` — `_id` is `rep:{tenant}:{destination}:{collection}`:

```json
{
  "_id": "rep:v1:backup:orders",
  "type": "state",
  "tenant": "v1",
  "destination": "backup",
  "collection": "orders",
  "key": "updatedAt",
  "cursor": { "value": "2026-09-19T10:00:00.000Z", "id": "..." },
  "resumeToken": { "_data": "8264F2…" },
  "status": "watching",
  "lastRunAt": "2026-09-19T10:05:00.000Z",
  "lastError": null,
  "stats": {
    "inserted": 0,
    "updated": 0,
    "deleted": 0,
    "batches": 0,
    "durationMs": 12
  },
  "pid": 4821,
  "hostname": "app-1",
  "updatedAt": "2026-09-19T10:05:00.000Z"
}
```

- `resumeToken` is the **stream position** — the oplog token of the last applied event. It is the real cursor, and it survives inserts, updates and deletes alike.
- `cursor` is the **backfill position** — where a cold-start pass resumes. `seed()` writes it.
- `status` is `watching` while a stream holds the collection, `running` during a backfill, `success` after a complete pass, `error` after a failure.
- `pid` / `hostname` say which process wrote it (`reusePort` / forked workers).

## Boot modes

What a process runs is described by four **capabilities** — `api`, `replication`, `scripts`, `sockets` — driven by `server.mode` (config) and by flags (**the flags always win**):

|                      | Flag                            | `server.mode`        | api | replication | scripts | sockets |
| -------------------- | ------------------------------- | -------------------- | --- | ----------- | ------- | ------- |
| Everything (default) | —                               | `'full'`             | ✅  | ✅          | ✅      | ✅      |
| Replication only     | `--replication-only`            | `'replication-only'` | ❌  | ✅          | ❌      | ❌      |
| API only             | `--api-only`                    | `'api-only'`         | ✅  | ❌          | ❌      | ❌      |
| No replication       | `--no-replication`              | `'no-replication'`   | ✅  | ❌          | ✅      | ✅      |
| Granular             | `--no-scripts` · `--no-sockets` | —                    | ✅  | ✅          | ❌      | ✅      |

```bash
bun index.ts                        # full
bun index.ts --replication-only     # a process dedicated to replication
bun index.ts --api-only             # the API and nothing around it
bun index.ts --no-replication       # a server that never starts the engine
bun index.ts --no-scripts           # a server that never runs the tenant scripts
bun index.ts --no-sockets           # a server without Socket.IO
bun index.ts --no-scripts --no-sockets
```

```typescript
app.boot({ server: { mode: "api-only" }, tenants: [/* … */] });
```

`api: false` also disables what the HTTP server carries (services, MCP tools, middlewares, routes, sockets) and the scripts, which run alongside it. `--replication-only` wins over `--no-replication` / `--api-only` when combined, and a warning is printed.

The banner only shows a `Mode:` line when something is disabled:

```
Replication: Off (api-only)
Mode: api-only (replication, scripts, sockets off)
Url: http://localhost:4000
```

### Replication-only process

It **exposes no API at all** — no HTTP server, no websocket handlers, no scripts, no services, no MCP tools, no middlewares. Useful to keep replicating from a host that must not serve traffic, to isolate replication from the application, or to run it in its own systemd/PM2 unit.

|               | Runs                                                                                                                                | Skipped                                                                                     |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **Loaders**   | tenant databases, collections, file collections, variables (`_vars_` replication filters on them), lifecycle                        | services, sockets, workflows, MCP tools, middlewares, routes, `createApp()` / `Bun.serve()` |
| **Lifecycle** | `beforeBoot` (before replication starts — the place to seed/reset it), `onDestroy` (on `SIGINT`/`SIGTERM`, after replication stops) | `afterBoot` (there is no listening server)                                                  |
| **Runtime**   | replication (change streams), distributed lock                                                                                      | `runScripts()`, cluster (master/workers), metrics & `/health`, JWT secret bootstrap         |

The process keeps itself alive (the open change streams hold it), and shuts down cleanly on `SIGINT`/`SIGTERM`: `onDestroy` hooks, then `stopReplication()`, then the database clients are closed.

### Who replicates

A collection is guarded by a **distributed lock** (`_locks_`, one per `(destination, collection)`), so only one writer owns it at a time — a one-shot backfill for the duration of its pass, or a change stream for as long as it watches. Two cluster nodes can therefore never replay the same oplog onto the same destination (Bun `reusePort`, forked workers, several containers).

The lock stores the **`pid`** and **`hostname`** of its owner, and so does every state document in `_replication_` (`pid`, `hostname`): you can see at a glance which process did what.

- a lock whose owner **died on the same host** is taken over **immediately** (the pid is probed) — a crashed worker never blocks replication for the whole TTL;
- a lock owned by **another host** can only be taken over once it expires (a foreign pid cannot be probed);
- releasing a lock only ever removes **our own** — a lock taken over by another node is never deleted from under it.

### No-replication / API-only processes

A **full** server — API, sockets, services, routes, scripts, MCP, middlewares, cluster, metrics — that simply **never starts the replication engine**: no change streams, no `_replication_` collection, no distributed lock. Nothing is written to the destination databases.

Use it when the same codebase is deployed in places that must not replicate (a read replica of the app, a staging environment pointed at production data, a machine where the destinations are unreachable) without stripping the tenant configuration. Per-tenant opt-out (`replication.enabled`) remains the finer-grained tool; `--no-replication` is the blunt, process-wide one. `--api-only` adds to that: no scripts, and Socket.IO is not served at all (`/socket.io/` answers like any unknown path).

## API

The replication engine is exposed under the `replication` namespace (like `cache`):

```typescript
import { replication } from "@anteros/core";

replication.start(); // connect destinations and open the streams (idempotent)
replication.stop(); // close the streams + the destination clients
await replication.now("v1"); // backfill what was never seeded, now
const state = await replication.state("v1", "backup"); // read _replication_ state
await replication.reset("v1"); // forget progress — the stream cold-starts again
await replication.seed("v1", "latest"); // set where the backfill starts
```

| Method                                        | Description                                                                    |
| --------------------------------------------- | ------------------------------------------------------------------------------ |
| `replication.start()`                         | Connect destinations and open one stream per replicated collection (idempotent) |
| `replication.stop()`                          | Close the change streams and the destination clients                            |
| `replication.now(tenantId?, opts?)`           | Backfill by hand what has never been seeded (see below)                         |
| `replication.state(tenantId, destinationId?)` | Read replication state from `_replication_`                                     |
| `replication.reset(tenantId, opts?)`          | Forget a tenant's replication progress (see below)                              |
| `replication.seed(tenantId, value, opts?)`    | Set where the backfill starts (see below)                                       |

`replication.now()` **seeds** what has never been backfilled (a fresh tenant, a destination restored from a backup). A stream already owns every replicated collection, and a run that finds the collection locked **skips it** — the destination is up to date by construction. `replication.reset()` is what re-arms a stream and forces a fresh backfill.

### Resetting replication

`replication.reset()` deletes the `_replication_` **state** (backfill position, resume token, stats, status), so the next run starts over. The destination data is **never** touched — only the bookkeeping is cleared.

```typescript
await replication.reset("v1"); // every destination + collection
await replication.reset("v1", { destination: "backup" }); // one destination
await replication.reset("v1", { collection: "orders" }); // one collection
```

| Option        | Type     | Default | Description                          |
| ------------- | -------- | ------- | ------------------------------------ |
| `destination` | `string` | all     | Only reset this destination id       |
| `collection`  | `string` | all     | Only reset this collection slug      |

**Returns** `{ tenant, state }` — the number of state documents deleted.

After a reset, the next cold start replays according to `initialSync` (`'full'` re-backfills everything, `'skip'`/`'latest'` resume without backfilling).

A **running change stream** holds its position in memory, so it is stood down **before** the state is cleared and re-armed right after: the stream cold-starts again from the cleared position (backfilling when the destination needs it) instead of silently restoring what you just forgot.

### Setting the start point

`replication.seed()` writes the `_replication_` backfill position directly — the counterpart of `reset()`. Use it to (re)start from a given point instead of copying everything; the stream picks up from there and carries every later change. The date field is the collection's replication key (`replication.key`, default `updatedAt`).

```typescript
await replication.seed("v1", "latest"); // from the latest document — skip existing
await replication.seed("v1", "now"); // from now — only future changes
await replication.seed("v1", "2026-01-01T00:00:00Z"); // from a date
await replication.seed("v1", new Date("2026-01-01")); // from a Date

// Scope + optional _id tie-breaker
await replication.seed("v1", "latest", {
  destination: "backup",
  collection: "orders",
});
```

| Value               | Behavior                                       |
| ------------------- | ---------------------------------------------- |
| `"now"`             | Start from now (same as `initialSync: 'skip'`) |
| `"latest"`          | Start from the latest `key` in the source      |
| ISO string / `Date` | Start from this date                           |

| Option        | Type     | Default | Description                |
| ------------- | -------- | ------- | -------------------------- |
| `destination` | `string` | all     | Only seed this destination |
| `collection`  | `string` | all     | Only seed this collection  |
| `id`          | `any`    | —       | Optional `_id` tie-breaker |

**Returns** `{ tenant, seeded }` — the number of state documents written.

A seed **replaces** the stream's position: the stream is stood down, the state is rewritten without a resume token, and it cold-starts again — backfilling from what you seeded, then tailing from there. That is also why `seed("v1", "now")` means "stop backfilling, watch from here" rather than "forget the history".

::prose-callout{variant="info"}

`reset()` + `seed()` are typically called from a **lifecycle `beforeBoot` hook** — where `replication` is tenant-scoped (like `rest`, no tenant id) — so a tenant can decide its starting point before replication starts. See [Lifecycle](/docs/reference/lifecycle).

::

## Limitations & notes

- **The oplog window is the retention of a stream** — a destination that is stale for longer than the oplog keeps the source data (writes are not replayed), and a resume token that has fallen out of the window restarts the stream from _now_. Take a destination offline for longer than the window and you need a full rescan: `replication.reset()`.
- **A replica set is required** — see [Requirements](#requirements). A standalone `mongod` gets an error per tenant and no replication at all.
- **A destination is a copy, not a cluster member** — one destination collection per tenant/collection pair, or two sources will overwrite each other's documents.
- **Initial backfill** — the first cold start copies the whole collection; it is batched and resumable, but large collections should be backfilled outside peak traffic.
- **A collection is written by one process** — the `(destination, collection)` lock is what makes the copy order-preserving. A destination reachable from two different replica sets would see two independent event orders.
- **Not a failover mechanism** — this engine copies data one way; availability, failover and promotion are MongoDB's job (replica set configured in the tenant's `database.uri`). See [Not a replacement for MongoDB replication](#not-a-replacement-for-mongodb-replication).
