## File Collections

Files are managed through dedicated **file collections**, defined in `**/*.file.ts` inside either `files/` or `collections/` for each tenant.

Unlike classic collections (documents), file collections are designed exclusively for file storage, validation and serving.

### Definition

```typescript
// files/photos.file.ts  — or collections/photos.file.ts
import { define } from "@anteros/core";

export default define.FileCollection({
  slug: "photos",
  fields: [
    {
      name: "description",
      type: "string",
      description: "Photo description",
    },
    {
      name: "author",
      type: "relationship",
      relation: { to: "users" },
    },
    {
      name: "alt",
      type: "string",
      description: "Image alt text",
    },
  ],
  upload: {
    allowedMimeTypes: ["image/jpeg", "image/png", "image/webp"],
    maxSize: 5 * 1024 * 1024, // 5 MB
    transformations: {
      width: 1200,
      format: "webp",
      quality: 80,
    },
  },
  storage: {
    driver: "disk",
    path: "uploads/photos",
  },
  api: {
    access: {
      "*": (ctx) => !!ctx.token.value, // auth required
      read: true, // public read (overrides `*`)
      delete: (ctx) => ctx.token.decoded?.role === "admin", // admin only
    },
  },
});
```

## Endpoints

| Method   | Route                                   | Description                     |
| -------- | --------------------------------------- | ------------------------------- |
| `POST`   | `/api/:tenant_id/upload/:slug`          | Upload **one or several files** |
| `GET`    | `/api/:tenant_id/files/:slug/:filename` | Serve / download a file         |
| `DELETE` | `/api/:tenant_id/files/:slug/:fileId`   | Delete a file (by `_id`)        |

### Upload

```bash
# Single file
curl -X POST /api/v1/upload/photos \
  -F "file=@photo.jpg"

# With custom fields (defined in fields)
curl -X POST /api/v1/upload/photos \
  -F "file=@photo.jpg" \
  -F "description=Profile photo" \
  -F "alt=My avatar" \
  -F "author=64f1a2b3..."

# Several files in ONE request (same field name, repeated)
curl -X POST /api/v1/upload/photos \
  -F "file=@a.jpg" \
  -F "file=@b.jpg" \
  -F "file=@c.jpg" \
  -F "album=Summer"
```

Response — **one file → a single object**, **several files → an array** (one document per file):

```json
{
  "_id": "507f1f77bcf86cd799439011",
  "createdAt": "2026-09-19T10:00:00.000Z",
  "updatedAt": "2026-09-19T10:00:00.000Z",
  "_file": {
    "filename": "507f1f77bcf86cd799439011.jpg",
    "name": "photo.jpg",
    "mimetype": "image/jpeg",
    "size": 2048576,
    "url": "/api/v1/files/photos/507f1f77bcf86cd799439011.jpg"
  },
  "description": "Profile photo",
  "alt": "My avatar"
}
```

```json
[
  {
    "_id": "...011",
    "_file": { "name": "a.jpg", "url": "/api/v1/files/photos/...011.jpg" },
    "album": "Summer"
  },
  {
    "_id": "...012",
    "_file": { "name": "b.jpg", "url": "/api/v1/files/photos/...012.jpg" },
    "album": "Summer"
  }
]
```

The form field must be named `file` or `upload` (repeated for multiple files). All other fields are stored in the document(s) alongside `_file`, **converted like a regular collection insert** (`toBson`): a `date` field sent as an ISO string is stored as a BSON `Date`, relationship ids become `ObjectId`, etc. The `_file` block is framework-generated and kept as-is.

Rules for multiple uploads:

- **One document per file** — each file gets its own `_id`, `_file` block, storage and replication.
- **Validation is per file** — MIME type and size (`upload.maxSize`) are checked for each file; one invalid file rejects the whole request (`MIMETYPE_NOT_ALLOWED` / `FILE_TOO_LARGE`).
- **Metadata is shared** — non-file fields apply to every uploaded document.
- `upload.maxSize` also caps the **total request** size, so the sum of all files must fit within it.
  The form field must be named `file` or `upload`. All other fields are stored in the document alongside `_file`.

### Serve a file

```bash
# Original version
curl /api/v1/files/photos/507f1f77bcf86cd799439011.jpg

# With transformations (images only)
curl "/api/v1/files/photos/507f1f77bcf86cd799439011.jpg?w=200&h=200&format=webp&q=80"
```

### Delete a file

Pass the document `_id` returned by the upload response:

```bash
# Use the _id from the upload response
curl -X DELETE /api/v1/files/photos/507f1f77bcf86cd799439011
```

> Unlike `GET`, the `DELETE` endpoint uses the document `_id` directly — not the full `_id.ext` filename. The server looks up the stored filename from MongoDB, deletes the physical file from storage, then removes the document.

## Image Transformations

Transformations are applied **on the fly** via query parameters on the `GET /api/:tenant_id/files/...` endpoint. No external dependency — uses `Bun.Image` (native).

| Parameter | Alias | Type                                | Description           |
| --------- | ----- | ----------------------------------- | --------------------- |
| `width`   | `w`   | `number`                            | Max width in pixels   |
| `height`  | `h`   | `number`                            | Max height in pixels  |
| `format`  | —     | `webp` \| `jpeg` \| `png` \| `avif` | Output format         |
| `quality` | `q`   | `number` (1–100)                    | Quality (default: 80) |

```bash
# 200×200 thumbnail in WebP quality 60
curl "/api/v1/files/photos/507f1f77bcf86cd799439011.jpg?w=200&h=200&format=webp&q=60"

# Width-only resize (height auto)
curl "/api/v1/files/photos/507f1f77bcf86cd799439011.jpg?w=300"
```

Transformations preserve the original aspect ratio (`fit: inside`) and never upscale the image (`withoutEnlargement: true`).

## Access Control

Each file operation can be protected individually via `api.access`:

| Rule     | Operation                                  | Description                               |
| -------- | ------------------------------------------ | ----------------------------------------- |
| `*`      | All                                        | Default rule when no specific rule is set |
| `upload` | `POST /api/:tenant_id/upload/:slug`        | Upload a file                             |
| `read`   | `GET /api/:tenant_id/files/:slug/:file`    | View / download                           |
| `delete` | `DELETE /api/:tenant_id/files/:slug/:file` | Delete                                    |

### Priority

1. **Specific rule** (`upload`, `read`, `delete`) — takes precedence
2. **Wildcard `*`** — applied when no specific rule is set
3. **No rule** — **access denied** (secure by default)

Each rule accepts a `boolean` or a function:

```typescript
api: {
  access: {
    '*': (ctx) => !!ctx.token.value,                                 // auth required by default
    upload: true,                                                    // public upload (overrides `*`)
    delete: (ctx) => ctx.token.decoded?.role === 'admin'             // admin only
    // 'read' inherits from '*' → auth required
  }
}
```

::prose-callout{variant="warning"}

If **no rule** is defined (neither `*` nor a specific rule), access is **denied** (`401 ACCESS_DENIED`). To explicitly allow access, define at least `'*': true`.

::

::prose-callout{variant="info"}

- **`true`** — allow without requiring a token (public access)
- **`false`** — deny immediately (no token needed)
- **`function`** — requires a valid token, evaluated at runtime

When a **function** is used, the token is mandatory. No token → `401 AUTH_REQUIRED`. Expired token → `401 TOKEN_EXPIRED`. Denied → `401 ACCESS_DENIED`.

::

### Handler Context

Access functions receive a `ctx` object:

```typescript
type FileAccessHandler = (ctx: {
  rest: useRest; // Rest instance scoped to the tenant
  error: fn.error; // helper to throw structured errors
  jwt: { sign; verify }; // JWT utilities
  token: {
    value: string | null; // raw JWT string
    decoded: Record<string, unknown> | null; // decoded claims
    provided: boolean; // token present in the request?
    expired: boolean; // token expired?
  };
}) => boolean | Promise<boolean>;
```

```typescript
// Handler examples
api: {
  access: {
    // Public — anyone can access
    read: true,

    // Blocked — no one can access
    delete: false,

    // Auth required
    upload: (ctx) => !!ctx.token.value,

    // Specific role
    '*': (ctx) => ctx.token.decoded?.role === 'admin',

    // Database check
    delete: async (ctx) => {
      const user = await ctx.rest.findOne('users', ctx.token.decoded?.sub);
      return user?.role === 'admin';
    },
  }
}
```

## Storage

### Disk (default)

```typescript
storage: {
  driver: 'disk',
  path: 'uploads/photos'   // relative to storage/
}
```

Files are stored at `storage/{tenant_id}/{collection}/{file_id}.ext`.

### S3

```typescript
storage: {
  driver: 's3',
  bucket: 'my-bucket',
  region: 'eu-west-1',
  path: 'uploads/photos'
}
```

S3 credentials are read from environment variables:

- `AWS_ACCESS_KEY_ID`
- `AWS_SECRET_ACCESS_KEY`
- `AWS_REGION` (default: `us-east-1`)
- `AWS_BUCKET`
- `S3_ENDPOINT` (optional, for S3-compatible backends like MinIO)

## Replication

Two distinct mechanisms, often confused:

|          | `replicate`                             | `replication`                                           |
| -------- | --------------------------------------- | ------------------------------------------------------- |
| What     | the **file binaries** (disk/S3)         | the **file documents** (metadata in MongoDB)            |
| Where to | S3 / SSH / SFTP                         | another MongoDB database (data replication engine)      |
| When     | on upload, right after the primary save | scheduled (cron / interval), incremental on `updatedAt` |

### File binaries — `replicate`

Uploaded files can be automatically replicated to multiple destinations (S3, SSH, SFTP) in parallel, without blocking the response.

```typescript
replicate: [
  {
    driver: "s3",
    bucket: "backup-photos",
    region: "eu-west-1",
    path: "replicas/photos",
  },
  {
    driver: "ssh",
    host: "backup.example.com",
    username: "deploy",
    path: "/backups/photos",
    privateKey: "/home/deploy/.ssh/id_ed25519", // optional
  },
  {
    driver: "sftp",
    host: "nas.local",
    port: 2222,
    username: "backup",
    path: "/mnt/storage/photos",
  },
];
```

| Option       | Type                          | Default       | Description                          |
| ------------ | ----------------------------- | ------------- | ------------------------------------ |
| `driver`     | `'s3'` \| `'ssh'` \| `'sftp'` | —             | Replication type                     |
| `host`       | `string`                      | `'localhost'` | Destination host (ssh/sftp)          |
| `port`       | `number`                      | `22`          | SSH/SFTP port                        |
| `username`   | `string`                      | `$USER`       | Remote username                      |
| `path`       | `string`                      | —             | Destination path                     |
| `bucket`     | `string`                      | —             | S3 bucket (required if driver: 's3') |
| `region`     | `string`                      | `us-east-1`   | S3 region                            |
| `endpoint`   | `string`                      | —             | Custom S3 endpoint                   |
| `privateKey` | `string`                      | —             | Path to SSH private key              |

::prose-callout{variant="info"}

SSH/SFTP authentication uses **SSH keys** by default. If `privateKey` is not provided, the default user key is used (`~/.ssh/id_rsa`, `~/.ssh/id_ed25519`). Password authentication is not supported.

::

## Audit & Tracking

Uploads and deletions are recorded in the audit trail (`_audit_`) with `collectionType: "file"` — the **metadata and the generated id**, never the stored document:

```json
// POST /api/v1/upload/photos
{
  "internal": false,
  "operation": {
    "action": "upload",
    "collection": "photos",
    "collectionType": "file",
    "status": "success",
    "input": {
      "file": {
        "name": "photo.jpg",
        "mimetype": "image/jpeg",
        "size": 2048576
      },
      "fields": ["description"]
    },
    "result": { "_id": "507f1f77bcf86cd799439011" }
  }
}
```

```json
// DELETE /api/v1/files/photos/507f1f77bcf86cd799439011
{
  "operation": {
    "action": "deleteFile",
    "collection": "photos",
    "collectionType": "file",
    "input": {
      "id": "507f1f77bcf86cd799439011",
      "filename": "507f1f77bcf86cd799439011.jpg"
    },
    "result": { "deleted": true }
  }
}
```

- `input.fields` lists the **names** of the custom fields sent with the upload — their values are not stored.
- `internal` tells an HTTP upload (`false`) from a server-side call to `handleUpload()` (`true`).
- A **served** file (`GET /api/:tenant_id/files/...`) is not audited — one entry per image would drown the trail. Uploads and deletions are.
- An upload rejected by validation (MIME type, size) is not audited either: only successful operations are.

See [Audit](/docs/reference/audit) for the full picture (redaction, retention, results policy).
