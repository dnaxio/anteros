## Workflows

Workflows allow you to execute a sequence of steps (`steps`) in an orchestrated manner, with progress tracking, database persistence, compensation on failure, and the ability to resume after failure.

Definitions are loaded from `workflows/**/*.workflow.ts` in each tenant.

## Loading

At boot, every `{tenant.dir}/workflows/**/*.workflow.ts` is imported and registered per tenant:

- **`enabled: false`** keeps a definition in the codebase without registering it (per environment, without deleting the file). `define.Workflow` sets `enabled: true` by default.
- A definition **without an `id`** is ignored with a warning — it is never registered under a bogus key.
- Two files declaring the **same `id`** for a tenant: the last one imported wins, and a warning names the file. A single entry is always kept.
- A file that **throws on import** is logged and skipped — it never hides the other workflows of the tenant (or of the other tenants).
- The banner shows what was loaded (`Workflows: 3 (v1, v2)`), and a `workflows: loaded` line is written to the log file.

## Definition

```typescript
// tenants/v1/workflows/order.workflow.ts
import { define } from "@anteros/core";

export default define.Workflow<{ amount: number; email: string }>({
  id: "process-order",
  name: "Process Order",
  description: "Process a customer order",
  version: 1,

  // Context fields with automatic MongoDB indexes
  context: {
    source: { type: "string", index: true },
    total: { type: "number", index: -1 },
  },

  steps: [
    {
      id: "verify",
      name: "Verification",
      exec: async ({ data, prevOutput, rest }) => {
        const user = await rest.findOne("users", data.userId);
        if (!user) throw new Error("User not found");
        return { verified: true };
      },
    },
    {
      id: "charge",
      name: "Charge customer",
      exec: async ({ data, prevOutput, rest, error }) => {
        if (data.amount <= 0) {
          throw error("Invalid amount", { code: "INVALID_AMOUNT" });
        }
        return { charged: true, transactionId: "tx_123" };
      },
    },
    {
      id: "notify",
      name: "Send notification",
      exec: async ({ data, prevOutput }) => {
        // prevOutput = { charged: true, transactionId: 'tx_123' } (from 'charge' step)
        return { notified: true };
      },
    },
  ],

  // Compensation: executed in reverse order when a step fails
  compensations: [
    {
      id: "refund",
      name: "Refund customer",
      depend: ["charge"],
      exec: async ({ data }) => {
        // Refund logic
      },
    },
  ],
});
```

### Configuration options

| Option          | Type                    | Default | Description                                                                                      |
| --------------- | ----------------------- | ------- | ------------------------------------------------------------------------------------------------ |
| `id`            | `string`                | —       | Unique workflow identifier (required)                                                            |
| `name`          | `string`                | —       | Workflow name (required)                                                                         |
| `description`   | `string`                | —       | Description                                                                                      |
| `version`       | `number`                | —       | Workflow version (stored in each run)                                                            |
| `enabled`       | `boolean`               | `true`  | Set to `false` to keep the definition without registering it                                     |
| `context`       | `WorkflowContextFields` | —       | Context field definitions with auto-indexing                                                     |
| `indexes`       | `WorkflowIndex[]`       | —       | Indexes to create on `_workflows_` — `{ key, name?, unique?, sparse? }`, including compound ones |
| `exec`          | `function`              | —       | Global handler executed before all steps                                                         |
| `steps`         | `WorkflowStep[]`        | —       | List of steps to execute                                                                         |
| `compensations` | `WorkflowStep[]`        | —       | Compensation handlers (reverse order on failure)                                                 |

### Context fields

Define context fields to store metadata about each run and create MongoDB indexes automatically:

```typescript
context: {
  source: { type: 'string', index: true },   // index asc on context.source
  total: { type: 'number', index: -1 },      // index desc on context.total
  date: { type: 'date', index: true },       // index asc on context.date
}
```

| Option  | Type                                 | Description                                    |
| ------- | ------------------------------------ | ---------------------------------------------- |
| `type`  | `'string'` \| `'number'` \| `'date'` | Field type                                     |
| `index` | `boolean` \| `1` \| `-1`             | Create MongoDB index (true/1 = asc, -1 = desc) |

The declaration is **enforced at `run()` time** — this is what `type` is for: a `string` field receiving a number, or a `date` field receiving something that is not a date, is rejected with `WORKFLOW_CONTEXT_INVALID` (400) instead of being stored silently. A `date` sent as an ISO string is **coerced to a real `Date`**, so the index on `context.<field>` stays typed. Undeclared keys are kept as-is: the declaration is a contract on what you declare, not a closed schema.

```typescript
await rest.workflow.run("invoice", data, {
  companyId: "acme", // string  ✅
  processedAt: "2026-03-04T05:06:07.000Z", // stored as a Date ✅
  anythingElse: { kept: true }, // undeclared → kept ✅
});
```

### Indexes

Beyond `context.index` (one field per declaration), `indexes` declares anything MongoDB supports — compound, unique, sparse, explicitly named:

```typescript
indexes: [
  { key: { "context.companyId": 1, status: 1 } }, // compound
  {
    key: { "context.batchId": 1 },
    unique: true,
    sparse: true,
    name: "uniq_batch",
  },
];
```

| Option   | Type                      | Description                                             |
| -------- | ------------------------- | ------------------------------------------------------- |
| `key`    | `Record<string, 1 \| -1>` | Fields, dotted paths allowed (`context.x`, `status`, …) |
| `name`   | `string`                  | Index name (default: MongoDB's `field_1_field_-1`)      |
| `unique` | `boolean`                 | Reject duplicate keys                                   |
| `sparse` | `boolean`                 | Skip documents missing the field (needed with `unique`) |

### Step options

| Option        | Type               | Default | Description                                                                        |
| ------------- | ------------------ | ------- | ---------------------------------------------------------------------------------- |
| `id`          | `string`           | —       | Unique step identifier (required)                                                  |
| `name`        | `string`           | —       | Step name                                                                          |
| `description` | `string`           | —       | Description                                                                        |
| `exec`        | `function`         | —       | Step handler (required)                                                            |
| `condition`   | `function`         | —       | Condition to execute or skip this step                                             |
| `compensate`  | `function`         | —       | Individual compensation handler for this step                                      |
| `depend`      | `string[]`         | —       | Step IDs this compensation targets                                                 |
| `retries`     | `number`           | `0`     | Attempts after the first failure — a transient error no longer rolls the saga back |
| `backoffMs`   | `number`           | `250`   | Delay before a retry, doubled on each attempt (capped at 5s)                       |
| `timeout`     | `string \| number` | —       | Abort the step after this duration (`'5s'`, `'2m'`, or ms)                         |

### Handler context

Each step `exec` (and compensation `exec`) receives:

```typescript
{
  data: TData,        // Business data passed to run() (typed via generic)
  prevOutput: any,    // Output of the previous step (null for first step)
  input?: any,        // Input defined on the step
  rest: Rest,         // Tenant-scoped client: rest.find, rest.insertOne, rest.workflow, rest.vars…
  agents: TenantAgents, // Tenant-scoped LLM registry — agents.get('support')
  api: Api,           // In-process facade over `rest` — bind a collection or a family
  error: fn,          // Throw structured errors
  jwt: jwt,           // JWT utilities
  signal?: AbortSignal, // aborted when the step exceeds its `timeout`
}
```

## Execution

### Run a workflow

```typescript
const run = await rest.workflow.run(
  "process-order",
  { amount: 50, email: "test@test.com", userId: "123" }, // data
  { source: "web", total: 50 }, // context (optional)
);
```

If the workflow completes successfully, `run` contains the full result. If it fails, the error is thrown.

### Pause a workflow

```typescript
const paused = await rest.workflow.pause(runId);
// true = a running run will stop at the next step boundary (reversible)
// false = nothing to pause (not running)
```

### Resume a workflow

```typescript
const resumed = await rest.workflow.resume(runId);
// Continues from the first non-completed step

// Refused (409/400) when the run is `completed`, `cancelled` or `compensated`,
// or when the workflow definition changed version since the run started —
// override the version guard deliberately:
await rest.workflow.resume(runId, data, { force: true });
```

### Resume all workflows

```typescript
const result = await rest.workflow.resumeAll();
// { resumed: 3, failed: 1 }

// Batched by `_id` (a large backlog is never loaded in memory at once)
await rest.workflow.resumeAll(undefined, { batchSize: 50 });
```

### Cancel a workflow

```typescript
const cancelled = await rest.workflow.cancel(runId);
// true = will stop at the next step boundary, and can never be resumed
// false = already terminal (completed, cancelled or compensated)
```

### Track progress

```typescript
const p = await rest.workflow.getProgress(runId);
// {
//   progress: 66,         // 0-100
//   status: 'running',    // pending | running | completed | failed | compensated | paused | cancelled | skipped
//   currentStep: 1,
//   totalSteps: 3,
//   totalExecuted: 1,
//   totalSkipped: 0
// }
```

### List runs

```typescript
const runs = await rest.workflow.listRuns("process-order");
```

### Query _workflows_ collection

```typescript
const all = await rest.workflows({ $match: { "context.source": "web" } });
```

## Run lifecycle

```
pending → running → [step 0 → step 1 → ... → step N] → completed
                         ↓ (failure)
                   compensations (reverse order) → failed
                         ↓
                      paused → resume() → running → ...
                      cancelled (irreversible)
```

## Compensation

When a step fails, compensation handlers are executed **in reverse order** for all previously completed steps. This allows undoing partial work (Saga pattern).

```typescript
compensations: [
  {
    id: "refund",
    depend: ["charge"], // Only runs if 'charge' step completed
    exec: async ({ data }) => {
      // Refund the customer
    },
  },
];
```

Each compensation step can target specific workflow steps via `depend`. If `depend` is not set, it matches by `id` (backward compatible).

A compensation that already succeeded is **never replayed**, and a run whose rollback completed becomes `compensated`: it can no longer be resumed (the steps were undone — replaying them would re-apply what was rolled back). A rollback interrupted by a crash is **finished** by `resume()` (not restarted), and a partially rolled back run stays `failed` until it is.

## Concurrency, pause & failures

| Situation                                                   | Behaviour                                                                                                                                                                                                                                                                          |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Two nodes advance the same run                              | One takes the **distributed lock** (`_locks_`, `workflow:<runId>`); the other gets `RUN_LOCKED` (409). The lock is released on the way out, and expires by itself if the node dies.                                                                                                |
| A forked worker (`reusePort`) dies mid-run                  | The lock records the **pid** and **hostname** of its owner: another process on the same host takes it over **immediately** (the pid is probed with `kill(pid, 0)`), instead of waiting for the 15-minute TTL. A lock owned by another host can only be taken over once it expires. |
| Our process loses the run (another node took the lock over) | The run stops at the next step boundary, without writing anything — the new owner has it.                                                                                                                                                                                          |
| `pause()` during a step                                     | The step finishes (its result **is** recorded), then the run stops: it stays `paused` and `resume()` continues at the next step — the completed step is never replayed.                                                                                                            |
| `cancel()` during a step                                    | Same boundary, but the run is terminal: it can never be resumed.                                                                                                                                                                                                                   |
| The step **fails** while a pause was requested              | The failure wins (the saga is rolled back) — a pause does not hide a failure.                                                                                                                                                                                                      |
| The step **fails** while a cancel was requested             | The cancel wins: the status stays `cancelled` and **nothing is compensated** (the operator asked to stop and leave the data alone).                                                                                                                                                |
| A step exceeds its `timeout`                                | The step is aborted (`WORKFLOW_STEP_TIMEOUT`), the ctx `signal` is aborted, and the run rolls back.                                                                                                                                                                                |
| A retryable error                                           | Retried up to `retries` times with an exponential backoff — no rollback when a retry succeeds.                                                                                                                                                                                     |
| Resume after a deploy                                       | Refused when the definition's `version` changed since the run started (`WORKFLOW_VERSION_MISMATCH`), unless `{ force: true }`.                                                                                                                                                     |

::prose-callout{variant="warning"}

**A step is at-least-once.** A process that dies **inside** a step leaves it `running`; the next `resume()` re-executes it, because the engine cannot know whether the side effect happened. Make your steps **idempotent** (a business key, an upsert, a `processed: true` marker) whenever they touch the outside world — a payment, an email, a third-party API.

::

There is **no transaction** spanning the run document and your step writes: the run state and the effects of a step are two separate writes. Idempotent steps (above) are what make that safe in practice.

### Who executes a run

Every run carries the **`pid`** and **`hostname`** of the process executing it (`_workflows_.pid`), and the lock in `_locks_` holds the same information — handy when the same code runs in several processes (Bun `reusePort`, `bun --watch`, several containers on one host):

```typescript
const run = await rest.workflow.getRun(runId);
run.pid; // 4242
run.hostname; // 'api-1'
```

## Retention

Runs are kept forever by default. Retention is opt-in, per tenant, and only prunes **finished** runs:

```typescript
app.boot({
  server: { workflows: { retention: "90d" } }, // default for every tenant
  tenants: [
    { id: "v1", dir: "v1", database: { uri: "…" } }, // → 90d
    {
      id: "v2",
      dir: "v2",
      database: { uri: "…" },
      workflows: { retention: "30d" },
    }, // → 30d
    {
      id: "v3",
      dir: "v3",
      database: { uri: "…" },
      workflows: { retention: false },
    }, // → kept forever
  ],
});
```

The TTL index is built on `completedAt`, which is only set when a run finishes: a run still `running`, `paused` or `failed` is **never** pruned. The tenant wins over `server.workflows.retention`, as everywhere else.

### Indexes

The loader creates the indexes `_workflows_` is queried with — only the missing ones, `background: true`, at boot and **without blocking it**:

| Index                              | Serves                                                       |
| ---------------------------------- | ------------------------------------------------------------ |
| `{ workflowId: 1, createdAt: -1 }` | `listRuns(workflowId)` — filter + sort                       |
| `{ status: 1 }`                    | `resumeAll()` — paused/failed sweeps                         |
| `{ 'context.<field>': 1 \| -1 }`   | every `context` field declared with `index: true \| 1 \| -1` |
| every `indexes[]` entry            | compound, `unique`, `sparse`, explicitly `name`d             |

The first two are the engine's own queries — without them, a runs listing scans the whole collection. The others come from your declarations: declare the context fields you filter runs by (e.g. a company, a batch, a date) and they are indexed for you. `_id` is always indexed by MongoDB. A failure is logged and never prevents the server from starting.
