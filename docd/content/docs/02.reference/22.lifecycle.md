Each tenant can declare a **lifecycle** — `{tenant.dir}/lifecycle.ts` — to hook into the server's boot and shutdown. It is **one file per tenant** (unlike collections, scripts or services, which are plural).

```typescript
// v1/lifecycle.ts
import { define } from "@anteros/core";

export default define.Lifecycle({
  beforeBoot: async ({ tenant, rest, logger }) => {
    await rest.insertOne("settings", { tenant: tenant.id, ready: true });
  },
  afterBoot: async ({ server, logger }) => {
    logger.info(`tenant ready on :${server.port}`);
  },
  onDestroy: async ({ reason }) => {
    await flushMetrics(reason);
  },
});
```

## Hooks

| Hook         | When                                                                                                                            | Context                                                               | On error                                                 |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- | -------------------------------------------------------- |
| `beforeBoot` | After databases are connected and collections are loaded — **before** replication starts and **before** the HTTP server listens | `{ tenant, rest, agents, api, logger, cfg, replication }`             | **aborts the boot** (`process.exit(1)`)                  |
| `afterBoot`  | Once the server is listening                                                                                                    | `{ tenant, rest, agents, api, logger, cfg, replication, io, server }` | logged — **never fatal**                                 |
| `onDestroy`  | On `SIGINT` / `SIGTERM`, before replication stops and DB clients close                                                          | `{ tenant, rest, agents, api, logger, cfg, replication, reason }`     | logged — shutdown proceeds (bounded by `destroyTimeout`) |

All hooks accept a sync or async function. `rest` and `replication` are **tenant-scoped** (like everywhere else) — no tenant id to pass.

### Options

| Option           | Type      | Default | Description                                                           |
| ---------------- | --------- | ------- | --------------------------------------------------------------------- |
| `enabled`        | `boolean` | `true`  | Turn the lifecycle off without removing the file                      |
| `destroyTimeout` | `number`  | `10000` | Max time (ms) allowed for `onDestroy` before shutdown proceeds anyway |

## Boot order

```
syncTenants()            → connect databases
syncCollections()        → collections + schemas   (required for `rest` to resolve collections)
syncFileCollections()
loadServices() / loadSockets() / syncWorkflows() / syncMcpTools() / loadTenantsMiddlewares() / loadRoutes()
loadLifecycles()         → import {tenant.dir}/lifecycle.ts
runBeforeBoot()          → beforeBoot hooks (awaited, fail-fast)
startReplication()       → replication starts
Bun.serve()              → server listening
runAfterBoot()           → afterBoot hooks
SIGINT / SIGTERM → runOnDestroy() → afterBoot done, onDestroy hooks run
```

Two ordering choices worth knowing:

- **`beforeBoot` runs before replication** — a seed or migration is already in the database when the first replication run happens. It is also the place to **reset or seed a replication** before it starts.
- **`beforeBoot` runs after every loader** — it can call `rest.runService()`, `rest.runAction()`, run workflows, etc. Everything is available.

### Controlling replication before boot

Because replication starts _after_ `beforeBoot`, this is where a tenant decides where its replication begins:

```typescript
// v1/lifecycle.ts
export default define.Lifecycle({
  beforeBoot: async ({ replication }) => {
    // Forget previous progress…
    await replication.reset();
    // …and restart from a given point instead of backfilling everything.
    await replication.seed("latest"); // or 'now', or a Date
  },
});
```

See [Replication → Setting the start point](/docs/reference/replication#setting-the-start-point).

## Cluster mode

In `reusePort` clusters, lifecycle hooks run **once**, in the process that owns the boot (the master or a standalone server) — never in the workers. This prevents a migration or seed from running N times (once per worker).

## Lifecycle vs Scripts

Both run tenant code around boot, but they answer different needs:

|                  | `Scripts` (`*.run.ts`)       | `Lifecycle` (`lifecycle.ts`)                      |
| ---------------- | ---------------------------- | ------------------------------------------------- |
| When             | ~150 ms after boot           | `beforeBoot` (blocking), `afterBoot`, `onDestroy` |
| Execution        | fire-and-forget, not awaited | **awaited**, ordered                              |
| Separate process | yes (`heavy: true`)          | no                                                |
| Use case         | optional / detached jobs     | **migrations, seeding, cleanup that must finish** |

Rule of thumb: _if it must be finished before serving, it belongs in `beforeBoot`; otherwise, use a Script._

## Notes

- Under `bun --watch`, every restart sends a signal, so `onDestroy` also runs in development — keep the hooks **fast and idempotent**.
- `onDestroy` runs **at most once per process**.
- A missing `lifecycle.ts` is fine: the tenant simply has no lifecycle.
