A **task** is a function the server runs on a cron schedule. Two things make it different from a bare `Bun.cron` call:

- the schedule, the time zone and `enabled` live in a **MongoDB row** (`_tasks_`), not only in code — you can disable a task, move it to Tuesday, or re-enable it **without a deploy**, and a **change stream** re-arms it immediately;
- the row survives a restart, so a redeploy never loses what an operator changed.

```typescript
// v1/tasks/weekly-report.task.ts
import { define } from "@anteros/core";

export default define.Task({
  id: "weekly-report",
  description: "Emails the weekly activity report.",
  schedule: "0 10 * * MON",     // every Monday at 10:00
  timezone: "Africa/Abidjan",
  run: async ({ rest, api, agents, logger, tenant, trigger, scheduledTime }) => {
    const orders = await api.collection("orders").countDocuments();
    logger.info(`weekly report for ${tenant.id}`, { orders, trigger });
    await rest.insertOne("reports", { at: scheduledTime, orders });
  },
});
```

## Finding the files

Tasks are loaded from each tenant's directory, recursively:

```
{tenant.dir}/tasks/**/*.task.ts
```

A file exports **one** `define.Task({ … })` as its default export. A broken file, an invalid schedule or a duplicate id is logged and skipped — it never hides the other tasks. A task with `enabled: false` in code is not registered at all.

## Options

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `id` | `string` | — **required** | Unique per tenant (plain identifier). It is the row's `_id` |
| `description` | `string` | — | What it does — served by `tasks.list()` |
| `schedule` | `string` | — **required** | A 5-field cron expression (`'0 10 * * MON'`) or a nickname (`'@daily'`, `'@weekly'`…) |
| `timezone` | `string` | server zone | An IANA zone (`'Africa/Abidjan'`) — the schedule is read in it |
| `enabled` | `boolean` | `true` | Declared default; the `_tasks_` row wins once it exists |
| `catchUp` | `'none' \| 'once'` | `'none'` | A process that was down at the fire time runs it **once** at boot |
| `lockMs` | `number` | `60_000` | How long one run holds the cross-process lock |
| `run` | `(ctx) => unknown` | — **required** | The handler — sync or async |

The schedule syntax is Bun's (`Bun.cron`): minute, hour, day of month, month, day of week; `*`, `,`, `-`, `/`; named months and weekdays (`MON-FRI`); nicknames (`@hourly`, `@daily`, `@weekly`, `@monthly`, `@yearly`). When both day-of-month and day-of-week are set, **either** matches — POSIX cron.

## The handler context

`run` receives the tenant's own tools, like any other server-side code:

```typescript
run: async ({ tenant, rest, api, agents, logger, task, trigger, scheduledTime }) => {
  // `task`    — the persisted row (schedule, timezone, lastRunAt, nextRunAt…)
  // `trigger` — 'cron' | 'manual' | 'catch-up'
  // `scheduledTime` — the occurrence's time (now, for a manual run)
});
```

There is no `io` in the context: a task runs before or independently of a socket connection.

## The `_tasks_` row

The first boot creates one row per declared task — **only when missing** (`$setOnInsert`). An existing row is never overwritten, so what an operator changed survives every deploy.

```json
{
  "_id": "weekly-report",
  "schedule": "0 10 * * MON",
  "timezone": "Africa/Abidjan",
  "enabled": true,
  "catchUp": "none",
  "lockMs": 60000,
  "lastRunAt": "2026-11-09T10:00:00.000Z",
  "lastStatus": "success",
  "lastDurationMs": 412,
  "nextRunAt": "2026-11-16T10:00:00.000Z",
  "lockedUntil": null,
  "removedAt": null,
  "createdAt": "2026-11-01T08:00:00.000Z",
  "updatedAt": "2026-11-09T10:00:00.412Z"
}
```

| Field | Written by | Meaning |
| --- | --- | --- |
| `schedule`, `timezone`, `enabled`, `catchUp`, `lockMs` | boot (once) / operator | What the scheduler obeys — the row wins over the code |
| `lastRunAt`, `lastStatus`, `lastError`, `lastDurationMs` | each run | The last run only — there is no run history table |
| `nextRunAt` | boot, arm, run | When the current schedule should fire next |
| `lockedUntil` | each run | The cross-process lock (see below) |
| `removedAt` | `tasks.remove()` | Set when the task is removed — the row stays so a boot never resurrects it |

## Changing a task without a deploy

An operator changes a row — through code or directly in MongoDB:

```typescript
import { tasks } from "@anteros/core";

await tasks.update("v1", "weekly-report", { schedule: "0 8 * * TUE" }); // move it
await tasks.update("v1", "weekly-report", { enabled: false });          // pause it
await tasks.update("v1", "weekly-report", { schedule: "0 10 * * MON", enabled: true });
```

`update()` validates the expression (`TASK_SCHEDULE_INVALID`, 400) and applies the change immediately. Every other process is notified by a **change stream** on `_tasks_` and re-arms or disarms its `Bun.cron` — no restart, no deploy:

```javascript
// directly in the shell — same effect
db._tasks_.updateOne({ _id: "weekly-report" }, { $set: { enabled: false } })
db._tasks_.updateOne({ _id: "weekly-report" }, { $set: { schedule: "0 10 * * MON" } })
```

A change stream needs a replica set. On a standalone MongoDB the boot still works: the warning is logged and edits apply on the next restart. Turn the watch off explicitly with `tenant.tasks.watch: false`.

## Removing a task

Disabling pauses a task; removing takes it out. The row is **kept** with a `removedAt` marker — that is what makes the removal durable: a boot finds the row and does not recreate it.

```typescript
await tasks.remove("v1", "weekly-report");   // disarmed everywhere, hidden from list()
await tasks.list("v1");                      // → no "weekly-report"
await tasks.list("v1", { includeRemoved: true }); // → still there, removed: true
await tasks.restore("v1", "weekly-report");  // back: enabled and armed
```

While removed:

- the change stream disarms the `Bun.cron` of every process;
- `list()` hides it unless `{ includeRemoved: true }`; `get()` still returns it (`removed: true`);
- `run()` and `update()` refuse it with `TASK_REMOVED` (409) — call `restore()` first;
- a restart does not bring it back (`$setOnInsert` never overwrites an existing row).

To remove it **for good**, delete the file that declares it, then delete its row:

```javascript
db._tasks_.deleteOne({ _id: "weekly-report" })
```

Once the file is gone, nothing recreates the row. (Deleting the row while the file still declares the task only removes the marker — the next boot declares it again.)

## Running one now

```typescript
const result = await tasks.run("v1", "weekly-report");
// { id, trigger: 'manual', skipped: false, ok: true, durationMs }
```

A manual run ignores the schedule but still takes the lock — it can be refused (`skipped: true`) when another run is in flight.

## Several processes

Every process arms its own `Bun.cron` (a cluster worker included), and each fire tries to take the row's lock:

```javascript
// atomic, in the collection — only one caller wins
findOneAndUpdate(
  { _id: "weekly-report", $or: [{ lockedUntil: null }, { lockedUntil: { $lt: now } }] },
  { $set: { lockedUntil: new Date(now + lockMs) } },
)
```

The winner runs, writes `lockedUntil: null` and the counters; the others skip. `Bun.cron` already prevents **overlapping runs inside one process** (the next occurrence is computed once the handler settles).

Two consequences worth stating:

- **Not exactly-once.** A crash between the handler and the counter update replays the occurrence — write your handlers to be idempotent (an upsert keyed by the occurrence date, for instance).
- **A hung run holds the lock** for `lockMs` (default 60 s). Raise it for a long job, or keep the job shorter than the lock.

## Missed occurrences

When the process was down at the fire time, `nextRunAt` stays in the past. On the next boot:

- `catchUp: 'none'` (default) — the occurrence is skipped, `nextRunAt` moves to the next one;
- `catchUp: 'once'` — the task runs **once** with `trigger: 'catch-up'` and `scheduledTime` set to the missed time.

```typescript
define.Task({ id: "invoice-batch", schedule: "0 2 * * *", catchUp: "once", run });
// Sunday's batch still runs if the server was down at 02:00 — once, not N times.
```

## Failures

A throwing handler does **not** crash the process (an unhandled `Bun.cron` rejection would). The error is:

- logged (`tasks: '<id>' failed for tenant '<tenant>'`, with the trigger and the code);
- written to the row — `lastStatus: 'error'`, `lastError: '<message>'`;
- returned by `tasks.run()` — `{ ok: false, error }`.

There is no built-in retry: a task is ordinary server-side code — call a workflow, a service, or `rest` and decide yourself.

## Configuration

```typescript
tenants: [{
  id: "v1",
  dir: "v1",
  database: { uri: "…" },
  tasks: {
    enabled: true,          // turn the scheduler off for this tenant
    collection: "_tasks_",  // where the rows live
    watch: true,            // re-arm on a change stream
  },
}]
```

## API

The `tasks` registry is importable from `@anteros/core` (it needs the tenant id, like `agents.get(tenantId, id)`):

| Method | Returns | Description |
| --- | --- | --- |
| `tasks.list(tenantId)` | `TaskInfo[]` | Every declared task, merged with its row (schedule, enabled, counters, `armed`) |
| `tasks.get(tenantId, id)` | `TaskInfo \| undefined` | One task |
| `tasks.update(tenantId, id, patch)` | `TaskInfo` | Change `schedule`, `timezone`, `enabled`, `catchUp`, `lockMs` |
| `tasks.remove(tenantId, id)` | `TaskInfo` | Remove it durably — disarmed, hidden from `list()`, not resurrected by a boot |
| `tasks.restore(tenantId, id)` | `TaskInfo` | Undo `remove()` — clears the marker, re-enables and arms it |
| `tasks.run(tenantId, id)` | `TaskRunResult` | Run now, under the lock |
| `tasks.ids(tenantId)` | `string[]` | Declared ids |
| `tasks.has(tenantId, id)` | `boolean` | Whether it is declared |
| `tasks.stats()` | `{ tenants, tasks, armed, running, started }` | This process's view |
| `tasks.sync()` / `tasks.start()` / `tasks.stop()` | — | What the boot does; exposed for scripts and tests |

Inside the HTTP API, `tasks` is **not** exposed as an action: a scheduled job is not a request. If a screen must pause a task, add a custom action that calls `tasks.update()` — access rules apply like anywhere else.

## Limits

- Tasks are loaded and armed in **API mode** only (`server.mode` with `caps.api`); a replication-only process does not run them.
- `_tasks_` holds the last run per task; it is not a history. For a trail, audit what the handler does (a `rest` write is audited).
- A file deleting its task is not propagated: the row stays. Use `tasks.remove()` to stop it durably, then delete the row once the file is gone (otherwise the next boot declares it again).
- A schedule is read in the row's `timezone`; DST follows Bun's semantics (a missing hour fires shifted forward, a duplicated hour fires once for a fixed time).
